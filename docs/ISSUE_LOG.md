### BK-44: a provider who gets paid outside Stripe had no way to record it (Nov 13, 2026)

Two accounting designs were possible for a directly-settled booking (client pays the provider cash/e-transfer, Berliz never touches the money): (a) treat it like any other booking with a `Payout` row for the provider's 85%, just skip the Stripe transfer part, or (b) recognize the provider already has their 85% in hand -- there is nothing for Berliz to pay out -- and track only the 15% commission as a debt owed separately. Went with (b): creating a normal `Payout` for money that was never going to move through Stripe would corrupt payout history (it would either double-pay the provider if a transfer were ever attempted, or sit as a permanently-fake "pending transfer" row that never resolves). A directly-settled booking now produces no `Payout` at all; only a `BookingSettlement` row, which exists purely to track the commission debt.

Asked the owner directly (not guessed) how that 15% commission debt actually gets collected, since Berliz has no payment instrument on file for most providers: **deduct it from the provider's next real Stripe payout.** `PayoutServiceImplement.attemptTransfer` now calculates any outstanding, uncollected settlement debt for that provider/center *before* calling Stripe, withholds it from the transfer amount, and only marks it collected *after* the (possibly reduced, possibly zero) transfer actually succeeds -- a failed Stripe transfer leaves every cent of the debt exactly as owed, never silently written off. A single debt row is never partially collected: if it doesn't fit entirely within the current payout, it waits whole for a later one. `Payout.settlementAmountDeducted` records how much of a given payout's "transfer" was really debt repayment rather than new money sent.

**Built** (mode a, direct settlement): `PUT /booking/settle/{id}` (confirmed+unpaid only; validates mode/amount/channel; accumulates onto any existing partial Stripe payment rather than overwriting it), `BookingSettlement` entity + migration `V105`, the withholding logic above, and a "Settle payment" button on the provider's booking card (`SettleBookingModalComponent`: amount pre-filled from the amount due, channel buttons, optional note). The client's own view shows "Paid via your trainer" instead of a dollar figure the provider could misreport; the provider's own view still shows the real amount. `com.berliz` commit `f674f4b`, `berliz` commit `d209b0695`.

### GN-59: sessions appeared to expire within minutes, repeatedly, especially right after a ReturnUrl sign-in (Nov 17, 2026)

Live evidence: a member's session dropped about 2 minutes after sign-in and kept dropping across 4 sign-ins in one QA run, each with "Your session expired." ReturnUrl sign-ins (where login redirects straight back into a `/dashboard` page) dropped fastest.

Checked the actual token/refresh machinery before assuming it was broken: it isn't. `JWTUtility` issues a 1-hour access token and a 30-day refresh token that rotates on every use; `AuthInterceptor` already has a correct, de-duplicated single-flight refresh-and-retry on any 401; `InactivityService`'s own 14-day idle timeout deliberately checks `getToken()` only, never the access token's expiry, with a doc comment explaining exactly why: "a merely *expired* access token... is still perfectly alive: the interceptor refreshes it silently." All of this predates this session (commits from August/September) and still looked completely sound.

**Root cause found:** `AuthService.isAuthenticated()` -- used for cosmetic display elsewhere, which is harmless -- was also being used by `AuthGuard` (every `/dashboard` navigation), `dashboardEntryGuard` (the lazy-route entry point ReturnUrl sign-ins land on first), `signedOutOnlyGuard`, the shop checkout gate, and the public-profile "quick add" gate, to decide whether to hard-redirect to `/login`. That method compares the access token's `exp` against `Date.now()` on the DEVICE's OWN clock -- the one thing `InactivityService` explicitly avoids doing. Any device whose clock runs ahead of the server's (not rare, and this project has already hit a real instance of exactly this class of clock problem -- see the BC-permanent-UTC-7 note) sees the access token as expired within minutes of it actually being issued, and a route guard has no 401 to trigger a silent refresh against -- it just bounces straight to `/login`, discarding a session whose 30-day refresh token (and real server-side session) was never actually at risk. A ReturnUrl sign-in re-enters a dashboard route almost immediately after login, so on a sufficiently skewed device it could fail on the very first post-login navigation -- matching "ReturnUrl sign-ins dropped fastest" exactly.

**Fixed** (`berliz` commit `f7740ca30`, merged into master): added `AuthService.hasSession()` -- "a token exists at all," the same reasoning `InactivityService` already had, now shared rather than duplicated (`InactivityService.hasSession()` delegates to it). Switched every hard "are you logged in" gate to it: `AuthGuard`, `dashboardEntryGuard`, `signedOutOnlyGuard`, `CartComponent#checkout`, `PublicProfileComponent#quickAdd`. `isAuthenticated()` itself is untouched and still used where the stricter, clock-sensitive check is actually correct (the STOMP connect's proactive-refresh trigger, and every purely cosmetic display -- navbar/hero CTA, footer "needs login" label, feedback modal -- where a wrong guess just self-corrects on the next load/refresh rather than logging anyone out).

**Not fixed, and out of scope here:** the underlying clock-skew itself, if that is in fact what QA's test device hit -- that's an environment/OS problem, not an app bug, and the fix above makes the app correct regardless of whether any given device's clock agrees with the server's.

### GN-51(a): production database backups -- built, and a real restore proven, not just claimed (Nov 18, 2026, owner-approved)

### GN-67: security event monitoring -- events grouped into incidents with an evidence ledger (Nov 18-20, 2026)

Lane 1 security, picked from the standing queue. Note on naming: earlier entries in this file ("State-integrity audit (GN-67/BK-45 class)", Nov 13) used "GN-67" as informal shorthand for a DIFFERENT concern (state derived live vs. stamped on the record) -- that was a mislabel, not this ticket. Spring Data (and the DB) make zero guarantee that insertion order survives a plain unordered query; this was never actually sorted, not a sorting bug introduced later. The "gibberish test entries" complaint is pre-existing QA/test data sitting in the table, not a code defect -- nothing here mass-deletes existing notification rows, since that's a production-data decision, not a bug fix.

**The real structural problem, and why this ticket needed a SEPARATE model, not a patch to `Notification`:** that generic inbox mixes "a client sent a message" and "failed-login spike on an account" as identical free-text rows with no severity or category distinction -- exactly the buried-alert story. Retrofitting severity onto 30-odd existing event types that already use `Notification` correctly was judged riskier than it's worth; instead, a new, narrow `SecurityEvent` -> `SecurityIncident` model, reusing PY-32's `TrialRiskAssessment` audit-row shape as the structural precedent (same project, same day, already-proven pattern for "one row per raw signal, admin-reviewable, never auto-acted-on").

**Built:**
- `SecurityEvent` (one row per raw signal) and `SecurityIncident` (migration `V114`, `com.berliz`): several events for the same `(eventType, subjectType, subjectId)` within a 24h window collapse into ONE incident instead of one row each -- `SecurityIncidentServiceImplement.raise()` does the grouping lookup and either attaches to an existing OPEN incident or opens a new one. Never throws (a monitoring write must not break the real action that triggered it).
- **The guardrail, enforced in code, not just documented:** `resolve()` is the ONLY method that ever changes an incident's status, is admin-only (`requireAdmin()`, the same manual `jwtFilter.isAdmin()` check this codebase already uses throughout rather than inventing a `@PreAuthorize` SpEL bean), only ever sets `ACTIONED` or `DISMISSED` (never anything resembling a block/suspend/hold verdict), and REQUIRES a non-blank note, appended (never overwritten) to the incident's `ledger` with who/when/what. Nothing that calls `raise()`, and nothing in `resolve()` itself, performs a block, suspension or payout hold -- an admin who decides to act does so through the platform's own existing tools (e.g. `updateUserStatus`) and records that decision here as the paper trail, which is exactly the ticket's "nothing acts without approval" line.
- **Two of the ticket's five defined event types wired to real, already-existing raw signals** (deliberately, not all five -- see below): **failed-login spikes**, via `LoginAttemptTracker` -- the moment an account's own 8-failures/15-minute lockout actually trips is reported once (`UserServiceImplement.raiseFailedLoginSpikeIfJustLocked`), reusing the tracker's own threshold rather than re-deriving it; **payout anomalies**, via the weekly automatic payout sweep (`PayoutServiceImplement.processWeeklyAutomaticPayouts`) -- a payout that was Stripe-ready and still failed to transfer used to be nothing but a `log.error` line, invisible to anyone not reading server logs, now also raises an incident.

### BK-54: the admin "add member" user dropdown rendered invisibly for a mouse user (Nov 18-20, 2026)

Owner-refined root cause (Nov 18): "the add-member dropdown data LOADS (about 38 options)... but the options panel never renders on screen; only blind keyboard selection works. Confirmed: `add-members-modal.component.html`'s User field is `<app-select>` (`SelectComponent`, `src/app/shared/select/`), the app's one shared searchable-dropdown wrapper around `@ng-select/ng-select`, opened from inside a `MatDialog`.

**Investigated, not guessed at.** Read `SelectComponent`'s own doc comment first: "the open list is attached to `<body>`, so a modal's overflow or the field below can never clip or hide it" -- `appendTo="body"` was the existing fix for a DIFFERENT, older problem (a modal with `overflow: hidden` clipping the panel). Traced the installed `@ng-select/ng-select` (v21.8.2) library's own actual positioning source (`ng-select-ng-select.mjs`) rather than assume: its `_updateXPosition()`/`_updateYPosition()` compute the panel's position as a RELATIVE offset between the trigger's and the append-target's `getBoundingClientRect()` values (not raw viewport/window-scroll math), and `_handleWindowScroll()` listens on `document` with `{ capture: true }`, which catches scroll on any ancestor scrollable container, not just the window -- both of two plausible "position math is wrong" theories (scroll-offset miscalculation, and an under-the-dialog's-overlay z-index loss) turned out to already be handled, or not conclusively provable, by reading the library's source alone. A genuinely invisible-but-functional panel (reachable by keyboard, never visible) is the signature of a STACKING-CONTEXT loss specifically -- the panel IS there and IS interactive, just painted behind something -- which no `z-index` value can be guaranteed to fix, because stacking contexts don't always compare the way raw z-index numbers suggest once multiple independent overlay systems (ng-select's own body-append, and Angular Material's CDK dialog/backdrop machinery) are both involved.

**Fixed, with real confidence, not a guess:** `@ng-select/ng-select` v21 ships built-in support for the browser's native Popover API (`[popover]="true"`) -- confirmed in its own source (`showPopover()`, feature-detected) -- which promotes the open list into the browser's **top layer**, a rendering layer that always paints above every normal (non-top-layer) element, by browser specification, regardless of z-index or which stacking context it's nested in. This is not a workaround; it's the library's own purpose-built answer to exactly this class of bug. Verified the library's own structural CSS (`ng-select.component.scss`) already declares `.ng-dropdown-panel { position: absolute; }` in an author-origin stylesheet, which correctly overrides the native popover's default UA styling (`position: fixed; inset: 0; ...`) per the CSS cascade (author origin always beats user-agent origin for equal-specificity, non-`!important` rules) -- so enabling popover mode doesn't fight the panel's existing JS-computed positioning.

**Enabled on `SelectComponent` globally** (`[popover]="true"` added alongside the existing `[appendTo]`), not scoped to just this one dialog -- it's the more correct realization of the component's own already-stated universal purpose ("a modal... can never clip or hide it"), and the library feature-detects `showPopover` itself, so an unsupported browser silently falls back to exactly today's behaviour. This can only help every other `<app-select>` usage inside a dialog across the app (equipment, payments, sub-tasks, tasks, testimonials modals all use it too), never regress one that already worked.

**Honest limitation: not live-verified.** The fix only needed an admin login to visually confirm, which this session's local dev database could have supported (29 real users exist locally) -- but setting a known test password on a local admin account to log in and check was explicitly declined (asked directly rather than guessed at or worked around), so this ships as a well-reasoned, source-verified fix rather than a confirmed one. ## Frontend CI was red on every push from Nov 21 morning through Nov 22 midday -- root cause and fix (Nov 22-23, 2026)

Called out in the owner's QA backlog: the `Frontend CI` workflow failed (or was cancelled) on literally every push to `master` for over a day, across many unrelated commits -- including several of the fixes documented just above in this same file. That directly contradicted every "full frontend suite green" claim made in those entries, which were all based on local `npx ng test` runs, not on what GitHub Actions was actually seeing. Opened the actual failing-step logs (`gh run view <id> --log-failed`) for the first time rather than trusting the "known pre-existing flake, not chased further" writeup two entries up -- that writeup was wrong. It is not flaky; it is 100% deterministic in a full-suite run, reproduced locally in ChromeHeadless on this exact commit on the first try, in isolation it always passes.

**Root cause:** `@ngrx/store/testing`'s `MockStore.overrideSelector()` (and `provideMockStore({ selectors: [...] })`, which calls it) does not override the selector per-`TestBed` -- it calls `selector.setResult(value)` directly on the real, module-level `createSelector`/`createFeatureSelector` function object, the same singleton every spec file imports (`node_modules/@ngrx/store/fesm2022/ngrx-store-testing.mjs`). `MockStore.resetSelectors()` is supposed to undo this, but nothing in the suite was calling it, so an override from one spec file stuck to that selector for the rest of the whole Karma process. `dashboard-top-users.component.spec.ts` (touched by this session's own GN-72/73/77/91 fix, two entries up) overrides `selectUsers` to a 1-item fake array in its last test and never resets it; `users.component.spec.ts`, which runs later in the same suite, then reads that same real `selectUsers` selector and gets the stuck fake array back instead of its own mocked empty state -- which is exactly why its "shows a retryable error" test saw `usersData.length === 1` instead of `0` and the error state's `*ngIf` never fired. Confirmed by bisection (`--include` on subsets) and a one-line debug log before fixing it, not by guessing. 62 other spec files across the suite do the same override-without-reset thing, so this was never going to be a one-file fix -- any of them could start poisoning some other test the moment Karma's file order shifted.

**The fix is NOT in `src/test.ts`**, even though that's the obvious place and even though `tsconfig.spec.json` lists it under `files`: Angular 16's `@angular-devkit/build-angular:karma` builder auto-bootstraps the test environment internally and globs `src/**/*.spec.ts` directly, so `test.ts` is never actually loaded into the Karma bundle at all -- confirmed with a `console.log` placed there that never fired, in any run. It's dead code today; left untouched. The real fix is a new `src/app/test-setup.spec.ts` (matches the glob, so it's guaranteed to load), containing a single top-level `afterEach` that calls `TestBed.inject(MockStore, null)?.resetSelectors()` after every test in the entire suite, regardless of which spec file set the override. A Jasmine top-level `afterEach` registered before `jasmine.execute()` begins applies globally no matter which file registered it or its position in the file list, so this closes the hole for all 62 files at once rather than patching `dashboard-top-users.component.spec.ts` alone and leaving the same landmine for the next spec file that overrides a shared selector.

Also fixed a second, unrelated, genuinely pre-existing failure the pollution bug had been masking: `provider-profile.spec.ts`'s `ProviderPackagesComponent` test still asserted the old `'$40 each'` wording, never updated when this session's own plan-pricing rewrite (two entries up) changed the headline to `'$40.00/ session'`.

**Verified, not just claimed this time:** full local suite 2513/2513 green in `ChromeHeadless` (same browser CI uses) both before fixing (4 failures, matching CI's exact failing test names) and after (0). Pushed; the resulting GitHub Actions run (`45089143670`) completed `success` -- the first passing `Frontend CI` run on `master` since the morning of Nov 21. `berliz`, this commit.

## GN-125: a search box's empty state said "No X yet" even when the query matched nothing (Nov 23, 2026)

Reported on the bookings search specifically (typing a client email that doesn't exist still said "No bookings yet", as if there were none at all), but the backlog explicitly asked for an app-wide audit, not a one-page fix. Root cause: `AdminSearchComponent` (`src/app/shared/admin-search/admin-search.component.ts`), shared by every admin list page, only ever emitted the filtered `results` array -- an empty array means either "nothing exists" or "nothing matched the query," and nothing crossed the component boundary to tell a host which. All 21 admin pages built on it had the same flat `*ngIf="data.length === 0"` -> static "No X yet." text, with zero query-awareness. 20 of their 21 container components also carried a dead `isSearch: boolean = true;` field -- hardcoded, never read anywhere -- that looks like an abandoned first attempt at exactly this fix; repurposed each into a real, wired `hasActiveQuery` field instead of adding a second redundant one.

**Fix, in three shapes:**
1. `AdminSearchComponent` gained `@Output() queryActive = new EventEmitter<boolean>()`, emitted alongside `results` at both points inside `runSearch()` (true/false mirrors whether the trimmed query is non-blank). New test coverage in `admin-search.component.spec.ts` (3 new tests: emits false up front, true once a non-blank query is active even with zero matches, back to false on `clear()`).
2. All 21 admin pages (bookings, users, trainers, todo-lists, testimonials, tasks, tags, subscriptions, payments, partners, newsletters, muscle-groups, members, exercises, contact-us, clients, centers, categories, trainer-pricing, sub-tasks, center-pricing) now wire `(queryActive)="onQueryActive($event)"` from `<app-admin-search>` into a tracked `hasActiveQuery` field, pass it down to their `-list` child as a new `@Input()`, and that child's empty-state text became a ternary -- e.g. `{{ hasActiveQuery ? 'No bookings match your search.' : 'No bookings yet.' }}` -- matching the pattern already used correctly elsewhere in the app (`admin-cms.component.html`, `dashboard-members.component.html`). The existing loading/error gating ahead of each list (e.g. bookings' `app-load-error`) is untouched; the ternary only applies once the list has genuinely resolved to empty.
3. Three non-admin, template-only fixes where `searchTerm` was already tracked but the empty-state text wasn't query-aware: `my-trainer-testimonials`, `my-trainer-like`, `my-trainer-clients` (all under `src/app/my-trainer/`).

**A real second bug found in the same sweep, not just wording:** `src/app/partner/center-like/center-like.component.html` gated both its empty-state (`*ngIf="centerLikes.length === 0"`) and its list wrapper (`*ngIf="centerLikes.length > 0"`) on the *unfiltered* count, while the `*ngFor` inside iterated the *filtered* `visibleLikes()`. A search matching zero existing likes left both conditions false (there *are* likes overall, so the empty state never showed; the filtered list has none, so nothing rendered inside the wrapper either) -- a blank area with no message at all, worse than wrong text. Fixed by switching both `*ngIf` gates to `visibleLikes().length`.

**Deliberately left alone** (confirmed correct or genuinely out of scope during the audit): `dashboard-members`, `members-directory`, `dashboard-exercises`, `find-providers`, `my-notifications`, `assign-workout-modal`, `my-workouts`, the equipment pages, `exercises-section`, the search-only widgets (`center-search`, `trainers-search`, `categories-search`, `global-search`), and `admin-cms` -- all already distinguish the two empty states correctly. `connections-main`, `runs`, `messages-main`, `message-popup`, `payment-codes`, the dead/unused `search-todo` component, and several admin pages with no search box at all (`berliz-feedback`, `payouts-list`, `faqs`, `problem-reports`, `profile-quiz-questions`) have no instance of this bug.
